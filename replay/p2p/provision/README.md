# Fixed-roster P2P provisioning

This package creates durable, invite-only membership for a deterministic P2P
match. It composes `replay/provision` enrollment and authenticated registration
with `replay/p2p/admission`. It never starts a simulation authority lease.

A room has a content ID, unique session ID and **durable player count (2–8)**.
The first enrollee administers invitations and creates the signaling room; every
participant has the same simulation role. All grants have `can_host`,
`trusted_authority` and `infrastructure` false. Those flags describe authority
permissions, not the ability to listen for P2P transport connections.

## Service ownership

Use one stable, serialized `Hub` per bounded deployment. `hub_open` loads the
entire existing room inventory before accepting requests; it refuses a player
count/content mismatch. `hub_receive` accepts the existing provisioning protocol
(Create, Invite, Join, Revoke). Existing `provision.Client`, `Enrollment_Journal`
and Godot `Provision_Connection` can carry these operations unchanged. The
deployment chooses content and player count; public callers cannot choose policy.

Use verified TLS for enrollment because requests contain bearer claims/invites
and replies contain private credentials. Transport connection/packet limits are
also required. The hub bounds room allocation and uses the same global and
per-connection enrollment token buckets as the authority provisioning hub.

`hub_control_receive` routes only authenticated Query, Challenge and Rebind.
It filters Start, Renew, nomination, takeover and the optional removal extension
before the existing MAC, nonce and sequence verifier. Each record stays at
authority epoch zero. Do not expose the embedded enrollment service through the
generic authority driver: use the P2P entry points.

Invites reserve their remaining uses against vacant fixed seats. Revoke releases
only unused reservations. Existing members never lose/recycle their seat through
invite revocation. Exact invite/enrollment retries still work after exhaustion;
changing the claim, original endpoint or ticket is a different request. Keys and
game tokens are independently generated by the existing enrollment service.

## Durability and reconnect

`Bundle` wraps the complete private enrollment record plus the fixed player count.
The commit callback must atomically compare the previous revision, persist the
whole bundle, and reject a changed player count for an existing room. Do not store
only `bundle.enrollment`: that would lose the fixed-roster contract.

The native `sqlite` package implements that contract with FULL/WAL transactions,
private files, canonical codecs, a separate `replay_p2p_provision` table, bounded
startup inventory and revision checks across service owners. Existing authority
room databases are not converted into P2P rooms. Uncertain creation fences the
hub; uncertain room mutations fence that room until authoritative storage is
reloaded. A committed join whose reply was lost returns the same credential on
retry after restart.

After receiving/reloading its grant, a new client process performs authenticated
Challenge/Rebind using a fresh RPC nonce. The member ID and key remain stable;
the service allocates a newer incarnation. It then queries the current roster.
`match_from_reply` must receive a reply already accepted by `auth.Rpc_Client`;
the helper itself is not a signature verifier. It checks the expected room,
content, player count, current local identity, complete enabled membership, and
absence of simulation authority.

`registry` returns Not_Ready until every seat is enrolled. Once complete, it
derives an ordered admission roster with session = room ID and P2P admission
epoch = 1 for the room's lifetime. A new match requires a new room ID. Rebinds
change credentials' incarnations without changing that roster or its code.
The public match descriptor contains no peer keys.

For Godot signaling, `rendezvous_p2p_room_provider` borrows the room and re-reads
committed membership on every callback. It stays inactive while enrollment is
incomplete, invalidates old incarnations immediately, and refuses a poisoned
room. Initialize `Rendezvous` with `mesh=true`. Destroy it before its room/hub.
Clients can pass the accepted descriptor and their current identity/key to
`rtc_p2p_config`. Multi-room signaling routing remains the deployment's job.

## Scope and acceptance

This supplies bearer room enrollment, not a human account system or matchmaking.
It does not change the P2P runner's fixed-roster disconnect/history policy, elect
a simulation host, or let late joiners replace departed players.

Run `tests/replay_p2p_provision/run.sh` for core/wire/client/provider tests and
WASM checking, `tests/replay_p2p_provision_sqlite/run.sh` for storage plus process
kills before/after commit, and `tests/replay_p2p_provision_service/run.sh` for the
native Godot TLS service/client fixture. The fixture provisions three members
through one client process; it is not a three-player gameplay or browser test.

The reusable [P2P party owner](../../godot/p2p_party.md) now connects these APIs
to Duel's browser and native create/join/rejoin flows. Local tests cover RTC and
encrypted ENet gameplay, plus fresh-process archive return. Public deployment,
broader recovery and human account integration remain open.
